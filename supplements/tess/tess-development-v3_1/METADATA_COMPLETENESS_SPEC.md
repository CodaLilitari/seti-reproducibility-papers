# Offline metadata completeness contract — development v3

Status: offline development contract, 8 October 2026. `metadata_contract.py` implements the narrow canonical-input validator described below; `test_metadata_contract.py` supplies its synthetic fixtures and eight acceptance cases. Test execution/results are owned by the coordinating worker and must be reported separately; this documentation correction runs no tests. Neither this document nor that validator implements or certifies a real MAST adapter, catalog query, product lookup, target acquisition, or flux analysis. No unfamiliar targets are acquired by this work. The proposal's other activation gates remain in force.

Reviewed source: `../TESS_SAMPLE_HOLDOUT_PROPOSAL_v2.md`, SHA-256 `6F7A556161415D04CFEFDEA94B2E62E446DDB078BB15C645DE096021144EA712`. V2 remains unchanged. This contract resolves three ambiguities: “finite” TIC IDs are insufficient; unavailable metadata must not be mistaken for a failed stellar cut; and “highest documented processing release” needs a predetermined comparison rule. It incorporates Lilitari's requested correction as relayed by Coda's coordinating task.

## 1. Interface and authoritative outputs

Implemented local interface, with no network-adapter or live-data validation claim:

```text
validate_metadata_batch(envelope, frozen_config) -> MetadataResult

MetadataResult.status = READY | PENDING | FAILED
MetadataResult.reason_codes = sorted list of stable machine-readable codes
MetadataResult.receipt = provenance, completeness checks, diagnostics
MetadataResult.selection = null unless status == READY
```

The validator receives only supplied in-memory data and configuration; it does not fetch, retry, sleep, read files, use the current clock, open flux, or discover additional targets. `envelope` contains exact `raw_json` text for canonical pages, their byte-length/hash/timestamp receipts, declared catalog provenance and observation/product inventories. **The validator checks each page's exact UTF-8 bytes and SHA-256, parses that JSON itself, and derives all typed/normalized records internally under frozen parsing and unit rules. There is no parallel caller-supplied decoded or normalized record authority.** Unexpected fields, including separately supplied `normalized_records`, fail schema validation. `frozen_config` contains the supported schema/missing-value policy, cuts, exclusions, query identity, pagination protocol, release comparator and sample size. Both complete inputs have deterministic content digests. Supplied retrieval timestamps are provenance, never tie-breakers.

For example, a hash-checked page containing `d=200` fails the distance cut. An accompanying caller-supplied normalized `d=20` cannot override it: that unsupported parallel input makes the batch fail. Altering the raw JSON without updating its byte length/hash also fails. Updating both the bytes and hash creates a different supplied input; a matching hash proves internal byte binding, not that those bytes truthfully came from MAST.

`READY` requires the entire required batch to pass completeness and structural validation. It returns the complete exclusion ledger, full eligible ordering, pool size, selected IDs, sector/product assignment manifest and selection digest. Fewer than 20 genuinely eligible hosts, including zero, is a valid result only for a complete batch; report the actual count and do not relax cuts.

`PENDING` means a required response, page, lookup or identity resolution is absent, unfinished or explicitly retryable. `FAILED` means supplied evidence violates the frozen contract or reports a terminal failure. If both occur, aggregate status is `FAILED` and retain every pending reason. Neither status returns an authoritative eligible pool, its count, sample hash, selected IDs or product assignments. Per-record diagnostic cut evaluations may be retained, explicitly marked provisional and non-selection-bearing. A diagnostic count of received rows is not an eligible-pool estimate.

No automatic retry or continuation is implied by either status. A later supplied complete batch is a new versioned validation input with linked provenance. Never silently alter an already frozen input or combine responses from different acquisition attempts without a declared compatible batch identity.

### Supported canonical schema and actual-MAST boundary

The current implementation accepts **one explicitly declared canonical offline wire format**. `make_fixture()` in `test_metadata_contract.py` is the complete accepted synthetic envelope/configuration example. Its `fixture://` identifiers, snapshot labels, release ranks and normalized JSON pages are invented test data, not MAST response samples. “Canonical” describes the fixed schema; page key order/whitespace need not be canonicalized before hashing, because the exact supplied UTF-8 text is hashed. Receipt and scientific-output digests use sorted-key compact JSON, UTF-8 and no non-finite JSON numbers.

The envelope has exactly `batch_id`, `synthetic`, `retrieval_started_at`, `retrieval_finished_at`, `availability_cutoff`, `catalog_snapshot_id`, `inventory_snapshot_id`, `catalog`, `observations` and `products`. The last two are maps keyed by canonical TIC ID. Every dataset has exactly `state`, `reason`, `snapshot_id`, `snapshot_evidence` and `pages`; supported states are `complete`, `pending` and `failed`. A page receipt has exactly `raw_json`, `sha256`, `byte_length` and `retrieved_at`. The JSON text itself contains the batch/dataset/TIC/request/schema/version/snapshot/cutoff identities, `index`, `next_index`, `terminal`, `total_rows`, `row_count`, `http_status`, `overflow`, `error` and `rows`, as enumerated by `PAGE_KEYS` in the implementation. There is no separate decoded-payload input.

Only `offline-metadata-v1`, `indexed-total-v1` pagination, `explicit-snapshot-ids-v1` consistency, `null-only` missingness and `positive-exact-canonical-v1` identity parsing are supported. Pages use zero-based consecutive integer indices, forward links, an explicit terminal page and consistent total row counts. Cursor-based or total-free protocols require a separately reviewed implementation/version; the present validator does not infer support. Frozen request records declare endpoint, parameters, exact projected fields and protocol evidence. The two mandatory exclusions, TIC 259377017 and TIC 4206066, must be present alongside the frozen additional exclusion list. Sample size is fixed at 20.

The three row schemas are exact: `tic-v8.2-normalized-v1` has `tic_id`, `Tmag`, `Teff`, `rad`, `logg`, `d`; `tess-observations-normalized-v1` has `tic_id`, `observation_id`, `sector`; `tess-products-normalized-v1` has `tic_id`, `observation_id`, `sector`, `mission`, `pipeline`, `cadence_seconds`, `kind`, `release`, `uri`, `pipeline_version`, `time_system`, `advertised_sha256`. Catalog scientific values must already be numeric in the fixed declared units or explicit JSON null; typing and finite-value checks occur internally. The code performs no undocumented unit conversion or catalog-sentinel interpretation. Product classification currently supports only the explicit labels TESS/SPOC/lightcurve; unfamiliar labels fail rather than becoming target exclusions. A positive integer cadence other than 120 seconds is known nonqualifying metadata. Qualified products require a mapped release and nonempty pipeline/time-system labels. An advertised product hash may be null; it is never substituted for an actually computed file hash.

Release ordering supports only a nonempty, explicitly versioned `explicit-rank-v1` mapping with documentary evidence and distinct integer ranks. Missing, unsupported or incomplete mappings fail; the validator does not guess semantic-version precedence. Supplied chronology must place the configuration freeze before acquisition start and page timestamps within the supplied batch interval. These checks establish consistency of the claims, not independent proof that the configuration was historically frozen at that time.

**Actual MAST response-byte binding is outside this implementation.** A future separately authorized adapter must preserve original service bytes and requests, validate the actual service schema/units/version/pagination/completeness/snapshot semantics, and establish an auditable transformation from those original bytes into this canonical input, including each field's source and any documented null or unit mapping. Hashing the canonical page does not establish that upstream transformation. A nonempty `snapshot_evidence` string, matching declared version, or `synthetic=false` flag does not certify a real remote snapshot. `READY` means only that the supplied canonical batch satisfies this offline contract; it does not certify original MAST acquisition, upstream conversion, remote completeness or flux authorization.

## 2. Record missingness versus acquisition failure

| Observed condition | Permitted interpretation |
| --- | --- |
| Complete, schema-valid catalog record explicitly marks a required stellar quantity missing/null under the frozen catalog policy | Record fails that cut; preserve its missing-value reason. |
| Complete record has a finite numeric stellar quantity outside an inclusive cut | Record fails that cut. |
| Explicit null in a canonical record, including one that a future audited adapter derives from a documented source sentinel | Record fails that cut. The current validator accepts only null and does not itself establish or perform an upstream sentinel conversion. |
| Required column absent because of truncation, omitted projection, schema drift, parsing error, or ambiguous omission semantics | Batch `PENDING` or `FAILED`; never call the host ineligible merely for this absence. |
| Complete observation/product inventory explicitly reports no matching product, or fewer than three distinct qualifying sectors | Record fails product availability; preserve its complete negative-result receipt. |
| Empty body, request error, timeout, missing page, partial response, unknown completion, overflow, or unresolved product/release lookup | Batch `PENDING` or `FAILED`; not a host exclusion and not permission to backfill. |

Use the specified filtered-MAST TIC fields `Tmag`, `Teff`, `rad`, `logg`, and **`d`**. Preserve `d` as distance in parsecs; do not substitute `dist` from another interface. This retains V2's previously checked official field mapping; this task performed no new network verification. A later adapter must verify its actual returned schema and units before normalization. Unexpected values or units cannot be silently coerced into cut failures.

Inclusive cuts remain Tmag 8–12, Teff 3000–5200 K, rad 0.15–0.85 solar radii, logg 4.2–5.2 cgs and d 5–100 pc. Numeric parsing, units and null-only missingness are frozen. Numeric strings, non-numeric sentinels and non-finite values fail the current canonical schema; a future adapter's documented conversion would need its own raw-byte lineage and validation. No imputation is permitted.

## 3. TIC identity and catalog provenance

The internally normalized TIC ID is a canonical base-10 string matching `[1-9][0-9]*`, representing a positive exact integer of arbitrary supported precision. Never pass IDs through a floating-point number. A losslessly parsed integer token is normalized; booleans, zero, negative values, fractions, floating-point representations (even `42.0`), exponents, NaN/infinity, already rounded numeric values and strings with leading zeros are invalid identity inputs. The current version has no option to normalize leading zeros. Catalog receipts retain the raw ID representation, canonical ID and decoded-row index; original representations remain in the retained page text. Numeric comparisons and tie-breaks use exact integer comparison, not string order or floating point.

An invalid or ambiguous ID blocks the batch: it cannot be reliably deduplicated, matched or ordered. Every observation/product inventory must link to exactly one validated TIC ID; unknown or conflicting associations also block the batch. Names, sky positions and approximate numeric matches cannot substitute for exact identity.

Store `catalog_name`, requested `catalog_version` (`8.2` here), returned version evidence, schema identity/digest and any provider snapshot/release identifier separately from `retrieval_started_at`, `retrieval_finished_at`, page timestamps and frozen availability cutoff. A retrieval date does not establish catalog version or an immutable snapshot. Requested version alone is insufficient evidence of returned version. A catalog version does not prove that a changing product service supplied a transactionally consistent inventory.

The frozen adapter protocol must define how pages belong to one complete compatible catalog/inventory view. If a consistent cutoff/snapshot cannot be established with the available metadata evidence, leave the batch pending or fail it; do not label it a certified frozen snapshot. Offline receipts validate the supplied evidence and its consistency, not the truth of unobserved remote service state.

## 4. Pagination and lookup completeness receipts

Before collection, pin exact request parameters, projected columns, endpoint/service identity, supported pagination mode, ordering/cursor semantics, terminal-page rule, overflow/error semantics and consistency policy. Their contract digest is part of the input. Do not assume a short page, HTTP success, or successful JSON parsing establishes completeness.

Each canonical page and its receipt record parent request/batch identity, page index, continuation information, retrieval timestamp, status/error/overflow indicators, byte length and SHA-256, declared schema/version, decoded row count, advertised total and explicit completion signal. Exact canonical page text must be retained. Validation checks its byte length/hash, rejects duplicate JSON keys and nonstandard JSON constants, parses it internally, and derives records solely from those decoded rows. No supplied decoded payload is trusted or reconciled against a separately authoritative normalized array. Synthetic receipts are labeled synthetic; original real-service byte preservation and conversion binding remain the future-adapter obligation stated above.

Batch validation checks that all expected canonical pages are present exactly once; index links terminate without gaps, unexplained overlap or cycles; query/config/schema/version identities agree; error and overflow flags are absent; returned row accounting agrees with advertised totals under the pinned protocol; and the terminal condition is present. Account separately for raw rows, repeated rows and unique TIC IDs. Deduplication must not conceal a pagination gap or allow an incomplete total to pass. The current implementation requires totals and indexed links. A future total-free protocol would need separately documented exhaustive termination and its own implementation/tests; an invented count comparison is not a substitute. A terminal marker without the promised earlier pages is incomplete.

Catalog completeness covers the entire declared query universe. Product completeness covers **every distinct host that passes catalog cuts and frozen pre-query exclusions**, before any host is ranked or the first 20 are taken. This exact required lookup set is derived offline from the complete catalog. Record explicit not-required reasons for excluded/catalog-ineligible hosts. Do not stop product lookup after 20 successes, use first-response order, or skip a slow host. Every required host gets separately complete observation and product receipts, including complete empty results. Unresolved lookup, pagination, cadence/pipeline classification or release identity for any required host blocks the whole batch.

Identical catalog duplicates collapse deterministically with all provenance retained. Conflicting complete catalog rows for one exact ID follow V2: fail that host's eligibility, retain every row and conflict reason, and never pick a convenient row. Incomplete acquisition is not a duplicate conflict. Define equality on the frozen required scientific fields, identity/version and meaningful classification fields after documented normalization; page position and retrieval timestamp are provenance, not scientific disagreement. Conflicting product rows that prevent a unique product identity or release determination block the batch rather than silently reducing its sector count.

## 5. Frozen release ordering and assignment

Before metadata acquisition, freeze a documented product qualification predicate for TESS, SPOC, two-minute light curves and positive exact integer sector number, plus an exact metadata-to-processing-release mapping. The release comparator must be a total ordering on every admissible release identifier: for example a provider-documented ordered integer/tuple or a pinned documented release-rank table. Preserve its version, source evidence, parsing rules and digest. Lexical version ordering is not a substitute for documented processing-release precedence. Do not improvise semantic-version parsing or treat observation date, retrieval time or first arrival as release rank.

Unknown or missing release identity, undocumented release order, or contradictory metadata produces `PENDING`/`FAILED`. Do not demote such products, call their sector unavailable, choose a lower release, or update the comparator during the batch. Resolving identity may require a separately authorized metadata/header-only step; until its receipt is supplied, this offline contract remains unresolved. A later changed comparator/configuration is a new proposal/input version, not a silent repair to the same frozen run.

For each host/sector, rank qualifying products by highest documented release, then **ascending lexicographic full product URI** as a literal UTF-8 string, with no locale-dependent comparison or unrecorded URI normalization. Retain all contenders, exact release keys and selection reasons. Exact duplicate product identities collapse. If the same release and URI carry conflicting identity metadata or asserted hashes, fail the batch; there is no arrival-order tie-break. URI alone does not prove processing version or future byte integrity.

After a complete eligible pool is established, apply V2's deterministic ID order: SHA-256 of UTF-8 `coda-tess-v1|` plus canonical TIC ID, ascending digest bytes, then ascending exact integer TIC ID for a hash tie. Select the first min(20, pool size). No other tie-breaker is permitted. Sector assignment remains earliest two distinct qualifying sectors for discovery and latest for holdout. Intervening sectors stay unopened. Three sectors must be distinct; duplicate products do not increase sector count.

Freeze selected URIs, releases, relevant pipeline/timing metadata and expected integrity evidence in the assignment manifest before flux acquisition. Do not invent a downloaded byte hash from a URI or a metadata label; record advertised hashes separately from later computed file hashes. Later unavailable/corrupt selected products remain acquisition failures attached to the fixed cohort. They do not authorize alternate products, alternate sectors, a replacement host or a second cohort.

## 6. Offline acceptance cases and invariants

These are acceptance expectations represented by the eight synthetic methods in `test_metadata_contract.py`. Their presence is not a test-pass claim; this documentation edit executes none:

1. Permute row order, page-processing order, duplicate arrival order and lookup-response order while preserving complete receipt semantics: identical classification, full eligible ordering, assignment manifest and selection digest. Provenance timestamps may differ without changing scientific outputs. Define canonical serialization and digest scope explicitly; receipt digests may differ while the scientific selection digest stays equal.
2. A complete record with explicit missing `d` fails its distance cut. The same apparent absence caused by a missing page, missing projection or ambiguous schema blocks the batch and produces `selection = null`. A hash-checked raw record with `d=200` cannot be overridden by separately supplied normalized `d=20`; the parallel authority is rejected. Tampered raw text fails byte/hash checks.
3. A catalog-eligible host with a verified complete two-sector inventory fails availability. The same host with two received sectors plus an unresolved next page blocks selection; no later host is substituted.
4. Reject invalid ID forms and precision loss; exactly order IDs beyond binary64's exact-integer range. Verify canonical hash input bytes and a forced hash-tie fixture resolved by exact integer ID.
5. Preserve consistent duplicates; record complete conflicting catalog duplicates as host ineligibility. Missing pages, cursor loops, incompatible totals, overflow or schema drift never become ordinary exclusions.
6. A product with unknown release ordering blocks the batch even if three other sectors appear usable. Permuted equal-release candidates select the same lexical URI; conflicting same-URI identity fails instead of depending on row order.
7. One unresolved required host blocks selection even if 20 other hosts are already fully eligible. Explicitly excluded/catalog-ineligible hosts require no product request, with that decision reproducible from frozen complete catalog input.
8. No API exposes “skip failures,” “fill to 20,” “best available,” or implicit release fallback. A later selected-product integrity/acquisition failure leaves original cohort membership and sample hash unchanged and records failure separately.

Passing these local cases would validate only the offline contract and its implementation against supplied canonical fixtures. An actual acquisition adapter still requires independent tests of original-response preservation, byte-to-canonical transformation lineage, service pagination/completeness semantics, schema/units/version evidence and snapshot consistency before any separately authorized unfamiliar-target run.
